# 微信云开发对现有设计的影响

配套 `api/types.ts` 与 `api/endpoints.md`。选用云开发（CloudBase）后，
下面 6 点会改动或简化已定的契约。

---

## 1. 「免鉴权接口」这个概念可以取消 ✅ 变简单

原契约里三个分享落地页要走无鉴权只读接口（赛事详情、项目详情、组队邀请）。

云开发里**没有这个问题** —— 小程序内 `wx.cloud.callFunction` 天然带 openid，
即使用户没注册过。所以：

- 不需要单独的无鉴权接口层
- 云函数里判断 `User` 记录是否存在即可，不存在就是"未注册"
- 登录墙仍然放在「报名 / 接受邀请」这一步，只是实现方式变成业务判断而非鉴权判断

> ⚠️ 但**返回体不得包含手机号**这条约束依然成立，且要在云函数里显式剔除字段。

## 2. 订阅消息大幅简化 ✅

云调用 `openapi.subscribeMessage.send` 不需要自己管理 access_token。
5 类消息（搭档邀请 / 支付提醒 / 候补转正 / 赛前提醒 / 待确认比分）都走这条。

## 3. 微信支付走「云支付」 ✅ 简化

云开发的云支付（`cloudPay`）省掉自建回调服务器和签名验签。
`POST /webhooks/wxpay` 变成一个支付回调云函数。

> 商户号与企业主体仍是硬前提，这条没变。

## 4. 定时任务用云函数定时触发器 ⚠️ 要合并

5 个 job 不要写成 5 个定时触发器。建议：

- **一个每分钟跑的扫描函数**，一次查出所有到期的 entry 并分派处理
- 理由：云函数定时触发器有数量和并发限制，且分散的触发器难以保证执行顺序

顺序很重要：`expire_payment` 释放名额后必须紧接着触发候补转正，
拆成两个独立触发器会出现空窗。

## 5. 数据库分页上限 ⚠️ 影响签表与榜单

云数据库单次查询上限：**小程序端 20 条，云函数端 100 条**。

| 场景 | 影响 |
|---|---|
| 签表（32 组 = 31 场） | 云函数端一次查得下，但要注意 `Match` 关联的 `Entry` 需二次查询 |
| 积分榜 | **必须分页**。一次 100 条，前端滚动加载 |
| 已报名组合列表 | 32 组以内没问题 |

建议：签表、赛程、榜单三个接口在云函数内做聚合，一次返回组装好的结构，
不要让小程序端多次查询拼装。

## 6. 名额判定用数据库事务 ✅ 支持

`accept` 的名额判定（见 endpoints.md §04）可以用 `db.startTransaction()`。
云开发数据库支持事务，能保证并发接受时不超发。

---

## 冷启动风险：今日比赛区

`GET /users/me/matches?scope=today` 是比赛日能否压回 2 tap 的关键。
云函数冷启动可能到秒级，球场边体验会很差。

对策（按性价比排序）：

1. **小程序端缓存**：进入赛事 tab 先渲染上次的今日比赛数据，再静默刷新
2. **数据裁剪**：这个接口只返回渲染卡片必需的字段，不要带完整 Match
3. 如果仍慢，考虑云函数预留实例（有成本）

## 组织者后台的结论

**第一版不做界面。**

| 操作 | 第一版怎么办 |
|---|---|
| 建赛事 / 开项目 | 云开发控制台手工录入 |
| 抽签 | 写成一个云函数，手动触发（随机 + 种子位） |
| 排赛程 | 云开发控制台，或一个 CSV 导入脚本 |
| 管报名 | 云开发控制台 |
| 改比分 / 确认结果 / 处理争议 | **小程序内**，赛事负责人的三个入口（阶段 0 已定） |

第二版再做网页后台：云开发**静态网站托管** + **Web SDK 手机号登录** +
复用同一批云函数。增量成本主要是前端界面本身。

> ❌ **组织者后台不要做进小程序。** 16 组签表的拖拽在 375pt 屏上不可能，
> 做出来也没人用。
