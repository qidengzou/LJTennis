01

实体关系

Entry（参赛主体）是整个模型的核心抽象：单打时 1 人，双打时 2 人。签表、赛程、比赛全部挂在它上面，所以单双打共用一套结构 —— 第一版只上双打，以后加单打不用重构。

02

报名状态机 · 工程版

和阶段 1 那张产品图的区别：这张标注了触发它的接口和负责超时的定时任务。三个等待态各有一个 job，缺一个就会有名额烂在手里。

三个 job 里最关键的是 job③

expire_promotion：候补转正后 24 小时未付款 → 作废并自动顺延下一位候补。业余赛退赛率高，这个任务会频繁触发；不实现的话每个空位都会烂在一个不响应的人手里。

03

鉴权：三个接口必须免鉴权

它们是转发卡片的落地页，也是唯一的获客路径。未登录用户要能完整浏览，登录墙放在「报名 / 接受邀请」这一步 —— 提前弹授权会直接劝退一半从群里点进来的人。

接口落地页约束
GET /tournaments/:id赛事详情返回体不得包含任何用户手机号
GET /events/:id项目详情
GET /entries/:id组队邀请

代价与收益

代价：后端要额外提供一套无鉴权只读接口。收益：分享链路不掉人。这是第一版唯一的获客路径，值得。

04

幂等与并发

两处必须做对，否则会丢数据或超发名额。

// 1. 记分提交必须幂等 —— 球场信号差，客户端会离线累积后重传
POST /matches/:id/score  { sets, serveOrder, version }

  version 不匹配   → 409 + 服务端当前 Match，由客户端决定合并还是放弃
  相同请求重放     → 200 + 相同结果，不产生副作用

// 2. 名额是竞争资源 —— accept 触发名额判定，必须在事务内完成
POST /entries/:id/accept

  BEGIN
    性别校验                 → 400
    IF feeCents = 0          → confirmed          // 免费捷径
    ELSE IF count < capacity → pending_payment    // + paymentDeadlineAt
    ELSE                     → waitlisted         // + waitlistPosition
  COMMIT

最关键的一个接口

GET /users/me/matches?scope=today。记分让出了 tab 位，比赛日能不能压回 2 tap 全靠赛事 tab 首页的今日比赛区置顶 —— 而那个区就是这个接口。它必须快、必须能缓存。

06

一个刻意的取舍：第一版不上传逐分数据

记分器在本地逐分记录（撤销、断网续记、杀进程恢复都要用），但上传时只传 sets 和 serveOrder。

逐分数据的唯一消费场景是发球统计（保发率、落点分布），第一版没有那个界面，存了是负担 —— 数据量大、还要设计归档策略。

要做发球统计时，加一个 points 字段即可，不影响现有结构。发球顺序已经记到人了，那才是难补的部分。

07

还阻塞着开发的三件事

1 · 组织者后台 —— 最大的缺口

本契约只覆盖选手端。建赛事、开项目、抽签、排赛程、管报名这些写操作的接口尚未定义。

赛事、项目、签表、赛程全部由组织者创建 —— 没有它，小程序里一条真实数据都没有，做出来是个漂亮的空壳。

2 · 积分规则

各轮次分值 · 赛事等级系数 · 双打各得全额还是各半 · 赛季划分方式。界面结构已定、不受规则影响，但没有规则算不出 PointRecord.points。

3 · 企业主体与微信支付商户号

支付和手机号授权的硬前提，行政流程可能数周。它不阻塞写代码，但阻塞上线 —— 建议现在就去办。
